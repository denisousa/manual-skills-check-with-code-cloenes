# Composite

## Purpose

Use this skill when **Composite** is the smallest credible pattern that can solve the problem without breaking PlatNexus layering, typed contracts, POSIX simulation paths, or hardware/board isolation.

## PlatNexus fit

- Category: `structural`
- Applicable layers: `services`, `utils`
- Recommended combos: `tree-configuration-processing`
- DesignMode seed: `Code/14`
- Pattern summary: Represent hierarchical configuration or resource trees uniformly.

## Use when

- The engineer needs to represent hierarchical configuration or resource trees uniformly.
- Similar responsibilities are repeating across a stable seam and would benefit from one clear pattern boundary
- The request explicitly asks for Composite or the symptoms map cleanly to it

## Avoid when

- A plain function, table, helper module, or existing abstraction already solves the problem cleanly
- The proposal adds vocabulary or indirection without improving ownership, lifecycle, or testability
- The design would leak board, RTOS, POSIX, chip, or vendor details upward into `services/`, `core_app/`, `examples/`, or `utils/`

## Checklist

### Generation checklist

1. Start from the smallest owning abstraction in the correct PlatNexus layer.
2. Keep public contracts strongly typed and platform-neutral.
3. Push concrete binding logic down into the lowest responsible layer.
4. Explain why **Composite** is better than a simpler non-pattern alternative.
5. Preserve Linux/POSIX host-simulated paths whenever the feature touches OSAL, HAL, or drivers.

### Review checklist

1. Is this truly **Composite**, or just renamed glue code?
2. Does the implementation preserve PlatNexus directory decoupling and ownership boundaries?
3. Are typed contracts kept intact without `void *` configuration creep or vendor leakage?
4. Does the proposal keep testability and POSIX simulation viable?

### Refactor checklist

1. Identify the current seam, coupling smell, or duplicated selection logic.
2. Move the minimum code necessary toward a real **Composite** structure.
3. Keep APIs stable unless the boundary itself is the bug.
4. Call out migration risks, simpler alternatives, and validation points.

## Refactor entry points

- Repeated `switch` / `if` selection logic around related implementations
- Platform conditionals climbing into `services/` or `core_app/`
- Copy-pasted lifecycle flows that want a cleaner seam or family boundary
