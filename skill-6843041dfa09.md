# Safe Refactoring Patterns

## Cardinal Rules

1. **Never refactor without tests.** If the code lacks tests, write characterization tests first that capture current behavior, then refactor.
2. **One change at a time.** Each refactoring step should be a single, independently verifiable transformation. Commit after each step.
3. **Run tests after every change.** If tests fail, revert the last step and try a smaller transformation.
4. **Refactoring changes structure, not behavior.** If you are fixing bugs or adding features, that is a separate commit.

## Extract Method / Function

### When to Use
- A block of code has a comment explaining what it does (the comment becomes the function name)
- A method is longer than 20 lines
- The same logic appears in multiple places
- A deeply nested block can be given a meaningful name

### Pattern
```typescript
// Before
function processOrder(order: Order): void {
  // Validate inventory
  for (const item of order.items) {
    const stock = inventory.get(item.sku);
    if (!stock || stock.quantity < item.quantity) {
      throw new InsufficientStockError(item.sku);
    }
  }
  // ... rest of processing
}

// After
function processOrder(order: Order): void {
  validateInventory(order.items);
  // ... rest of processing
}

function validateInventory(items: OrderItem[]): void {
  for (const item of items) {
    const stock = inventory.get(item.sku);
    if (!stock || stock.quantity < item.quantity) {
      throw new InsufficientStockError(item.sku);
    }
  }
}
```

### Checklist
- The extracted function has a clear, descriptive name
- Parameters are minimal (pass only what is needed)
- Return values are explicit (avoid mutating parameters)
- The original call site reads like a summary of the operation

## Extract Class

### When to Use
- A class has multiple unrelated responsibilities (violates SRP)
- A subset of fields and methods always travel together
- The class exceeds 300 lines

### Pattern
```python
# Before: User class handles both profile and notification logic
class User:
    def __init__(self, name, email, slack_webhook, email_prefs):
        self.name = name
        self.email = email
        self.slack_webhook = slack_webhook
        self.email_prefs = email_prefs

    def send_slack(self, message): ...
    def send_email(self, subject, body): ...
    def update_profile(self, name, email): ...

# After: Extract NotificationService
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email

    def update_profile(self, name, email): ...

class NotificationService:
    def __init__(self, slack_webhook, email_prefs):
        self.slack_webhook = slack_webhook
        self.email_prefs = email_prefs

    def send_slack(self, message): ...
    def send_email(self, subject, body): ...
```

## Inline

### When to Use
- A function does nothing more than delegate to another function
- A variable is used only once and adds no clarity
- An abstraction is more confusing than the implementation it wraps

### Anti-Pattern: Over-Inlining
Do not inline if the extracted name adds clarity or the logic is used in multiple places.

## Rename

The most common and most valuable refactoring.

### Guidelines
- Names should reveal intent: `d` becomes `elapsedDays`, `tmp` becomes `filteredResults`
- Use your IDE's rename refactoring to update all references atomically
- Boolean names should read as questions: `isValid`, `hasPermission`, `canRetry`
- Functions should use verb phrases: `calculateTotal`, `fetchUserById`, `validateInput`
- Avoid abbreviations unless universally understood (`id`, `url`, `http`)

### Across Boundaries
When renaming public API surfaces (function signatures, endpoints, database columns):
1. Add the new name alongside the old one
2. Migrate all callers to the new name
3. Remove the old name
4. This is a three-step process across multiple deployments

## Move

### When to Use
- A function uses more from another module than from its own
- A class is in the wrong package/directory based on domain boundaries
- Circular dependencies indicate misplaced code

### Process
1. Copy the function/class to the new location
2. Update the old location to re-export from the new location (keeps existing imports working)
3. Update all imports to point to the new location
4. Remove the re-export from the old location

## Change Signature

### When to Use
- A function takes too many parameters (more than 3-4)
- Parameters are frequently passed as a group
- A boolean parameter controls branching (replace with two functions or an enum)

### Pattern: Parameter Object
```go
// Before: too many parameters
func SendEmail(to, from, subject, body string, cc []string, isHTML bool, 
    attachments []Attachment, replyTo string) error { ... }

// After: parameter object
type EmailMessage struct {
    To          string
    From        string
    Subject     string
    Body        string
    CC          []string
    IsHTML      bool
    Attachments []Attachment
    ReplyTo     string
}

func SendEmail(msg EmailMessage) error { ... }
```

### Pattern: Remove Flag Arguments
```typescript
// Before: boolean controls behavior
function getUsers(includeInactive: boolean): User[] { ... }

// After: separate functions with clear intent
function getActiveUsers(): User[] { ... }
function getAllUsers(): User[] { ... }
```

## Strangler Fig Pattern (Large Rewrites)

For replacing a large legacy system without a risky big-bang rewrite.

### Process
1. **Identify a seam** -- find a boundary where new code can intercept calls to the old system
2. **Build a facade** -- route traffic through a thin layer that delegates to the old system
3. **Implement one slice** -- rewrite one feature behind the facade, routing its traffic to the new code
4. **Verify parity** -- run old and new in parallel, compare outputs (shadow traffic or feature flags)
5. **Migrate traffic** -- switch the facade to route this feature to the new code
6. **Repeat** for each slice until the old system handles no traffic
7. **Remove the old system**

### Rules
- Never rewrite more than one slice at a time
- Each slice must be deployable independently
- Keep the facade as thin as possible -- it is temporary scaffolding
- Use feature flags to control rollout and enable instant rollback
- Measure: response times, error rates, and data consistency at each step

### Anti-Patterns
- **Big bang rewrite** -- rewriting everything at once while the old system keeps evolving
- **Parallel maintenance** -- running both systems indefinitely without a plan to decommission the old one
- **Scope creep** -- adding new features during the rewrite instead of achieving parity first

## Code Smells That Signal Refactoring

| Smell                  | Refactoring                          |
|------------------------|--------------------------------------|
| Long method            | Extract method                       |
| Large class            | Extract class                        |
| Long parameter list    | Introduce parameter object           |
| Duplicated code        | Extract method, pull up to base      |
| Feature envy           | Move method to the envied class      |
| Data clump             | Extract class for the clump          |
| Boolean parameter      | Replace with separate methods        |
| Deeply nested branches | Extract method, guard clauses, early return |
| Shotgun surgery        | Move related code into one module    |
| Dead code              | Delete it (git remembers)            |
